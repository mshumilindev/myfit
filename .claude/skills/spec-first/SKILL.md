# Spec-first і малі партії

Коли: нова фіча, spike, зміна що торкається даних/rules/кількох екранів/ролей. Не потрібно для очевидного фіксу в одному місці.

1. **Розвідка:** найближчий аналог у репо (`rg`), `docs/MVP.md`, `docs/FEATURES-AC.md`, макети, `docs/UI-KIT.md`. Скоуп не міняй мовчки; суперечність із кодом чи доками — винеси питанням.
2. **Інтерв'ю (коротко):** лише те, що змінює дизайн і не виводиться з коду/доків; питання з варіантами та рекомендацією. Решту вирішуй сам і записуй у spec.
3. **Spec:** `docs/specs/<slug>.md` за `docs/specs/TEMPLATE.md` — мета, поза скоупом, AC з доказами, підхід (+альтернативи з ціною), вплив на кіт/дані/безпеку/i18n/offline, план тестів (red/green), реліз і відкат, партії. Тримай стисло (1–2 екрани).
4. **Погодження:** покажи spec користувачу; незворотне й неоднозначне — до коду. Погоджене фіксуй у задачі Linear (посилання на spec, AC перенесено в опис).
5. **Партії:** розбий на малі кроки; кожен = один AC або зв'язна група, один коміт/PR, зелений гейт, відкат дешевий (окрема гілка/worktree для великого). Далі цикл `work-issue`.
6. **Ризикове** (шифрування, rules, міграції, ролі) — незалежне рев'ю `risk-reviewer` перед закриттям.
7. **Після:** spec лишається у `docs/specs/` зі статусом «готово»; розбіжності з реалізацією виправ у spec.
