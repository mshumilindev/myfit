# ADR 014 — gitleaks: сканування секретів по всій історії (SPO-58)

**Статус:** прийнято (04.11.2026), рішення власника «так».

**Контекст.** Було лише Semgrep `p/secrets` з `|| true`: знахідки анотації, але не блокують merge. Секрет у коміті лишається в історії назавжди, тож перевірка має бути блокуючою.

**Рішення.** Окремий паралельний job `Secret scan (gitleaks)` у CI: `gitleaks/gitleaks-action@v2`, `fetch-depth: 0` (вся історія), набір правил за замовчуванням плюс `.gitleaks.toml` з винятками лише для шляхів із несекретними схожими рядками (lock-файл; `generic-api-key` лише в `client/src/`, де це імена ключів localStorage, тексти лендингу й мок-id у тестах; публічний веб-ключ Firebase в `client/src/firebase.ts`). Перший повний прогін дав 40 знахідок, усі переглянуті вручну як хибні. Action на push сканує лише останній коміт, тому другий крок проганяє бінарник по всій історії. Job входить у `needs` воріт `quality`, тож червоний скан блокує merge. Інструмент не потрапляє в бандл і `package.json`.

**Альтернативи.** trufflehog (повільніший, мережеві перевірки токенів надсилають їх сторонньому сервісу: ні); лише Semgrep (не сканує історію, не блокує); pre-commit хук (залежить від бінарника на кожній машині; можна додати згодом). Ціна: ~30–60 с паралельного job, бюджет CI не збільшується.

**Правила.** Знайдений секрет: ротація ключа першою, потім видалення; allowlist розширюється лише з поясненням у PR. `gitleaks-action` для організацій вимагає ліцензію; репозиторій особистий. Якщо GitHub переведе репо в організацію, замінити крок на бінарник gitleaks.
