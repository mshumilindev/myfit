# SPO-184 · на якому шарі блокувати країни (висновок спайку)

Дата: 2026-10-29. Інженерний документ, не юридична консультація. Рішення делеговано власником («вирішуй сам за вимогами закону й практиками»). Усе нижче має джерело; чого не перевірено, так і написано.

## Висновок

**Cloudflare Free перед `myspotter.fit` + Worker** (`edge/geo-block/`). Країна береться з `request.cf.country`, який Cloudflare виставляє на краю; клієнт не може його задати. Країни: `RU, BY, KP, IR` у конфігу (`BLOCKED_COUNTRIES`). Невідоме розташування пропускається.

## Чому не інше

| Варіант                                 | Результат дослідження                                                                                                                                                                                                                                                                                                                                      |
| --------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Firebase Hosting сам                    | У документації правил (rewrites/redirects/headers) немає гео-правил (прочитано перші ~100 тис. символів сторінки конфігурації: відсутність не доведено повністю). Hosting-сторінки заголовка країни не згадують.                                                                                                                                           |
| Заголовок країни у Functions за Hosting | Співробітник Firebase в обговоренні писав, що `x-appengine-*` для функцій за Hosting «неточні»; недокументований `x-country-code` не стабільний. Будувати на цьому не можна. Джерело: groups.google.com/g/firebase-talk/c/YQL6LmF_Mqo                                                                                                                      |
| Cloud Armor + зовнішній балансувальник  | `{client_region}` від балансувальника надійний (перезаписує клієнтські заголовки), але за опублікованими тарифами ≈ $18 (одне правило пересилання) + $5 (політика) + $1/правило на місяць: **≈ $24+/міс** (моя арифметика з погодинних ставок, мінімум не підтверджено). Бюджету немає. Hosting не є бекендом балансувальника (не підтверджено, що можна). |
| Ingress `internal*` для Cloud Run       | Hosting-rewrite потребує `all`; з Hosting не поєднується.                                                                                                                                                                                                                                                                                                  |
| Перевірка лише в клієнті                | Легко обійти; потребує стороннього IP-сервісу (приватність).                                                                                                                                                                                                                                                                                               |

Cloudflare: правило країни в WAF Free доступне, але **кастомна сторінка блокування WAF лише з Pro** (developers.cloudflare.com/waf/custom-rules/create-dashboard/). Тому сторінку віддає Worker (безкоштовний). `request.cf.country`, `regionCode`, `latitude`, `longitude`, `asn` доступні на всіх планах (developers.cloudflare.com/workers/runtime-apis/request/).

## Чого це не закриває

Прямі `*.web.app` / `*.firebaseapp.com`, `cloudfunctions.net`, `run.app`; Firestore, Storage, Auth REST (клієнтський SDK кличе їх напряму); користувачі з кешем Service Worker; VPN і невизначені IP. Для цих шарів документовано лише частковий засіб: Auth blocking `beforeSignIn` бачить `ipAddress`, але потребує Identity Platform (ціна не перевірена) і власної IP→країна бази.

## Ризики активації

- Верифікація домену Firebase за проксі: у спільноті Cloudflare є скарги, офіційного рішення немає. Тому порядок: спочатку DNS only, потім проксі, SSL режим Full (README у `edge/geo-block/`).
- GDPR: Cloudflare обробляє IP як процесор (DPA із SCC входить у self-serve угоду: cloudflare.com/gdpr/introduction/). У політику, `processors.md` і реєстр даних вносимо **в день активації** (до того процесор не діє).

## Рішення, ухвалені за власника (можна змінити)

1. Країни: RU, BY, KP, IR (список у вашій задачі SPO-220), конфіг.
2. Fail-open для невідомого розташування.
3. Безкоштовний шар (Cloudflare) замість ~$24+/міс; чесно описана неповнота.
4. Сторінка: HTTP 451, 5 локалей, без редиректів і кешування.

## Що потрібно від власника

Дія з акаунтами: Cloudflare + NS у Porkbun (інструкція в `edge/geo-block/README.md`). Живий домен без вашого «так» я не чіпаю.
