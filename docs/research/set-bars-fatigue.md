# Смужка сету як «бак»: що відомо про втому всередині сесії (SPO-151)

Статус: дослідження для `docs/specs/set-bars-tank.md`. Дата: 2026-10-17. Код не змінювався.
Суміжні доки (не змінюємо): `docs/research/warmup-fatigue.md` (формула жорсткості розминки через RIR),
`docs/research/detraining.md`.

## 1. Питання

Ліва смужка рядка сету в живій сесії має означати одне: **скільки готовності лишилось у цільового м'яза
для цієї вправи** («бак»). Вона має падати від сету до сету, ніколи не зростати «з нічого», частково
відновлюватись лише відпочинком, враховувати: (a) наскільки м'яз відновився з минулих сесій,
(b) що цей м'яз уже зробив сьогодні в інших вправах, (c) власні сети вправи (вага відносно реального e1RM,
повтори, запас повторів, тип сету), (d) час відпочинку. Нових полів і змін шифрування немає.

### 2.1 Де і для кого смужка

- Смужка є лише при `focusView && live && isStrengthExercise(ex)` (`SessionView.tsx:3148`, `live` = `finishedAt === null && !props.past`, рядок 684).
  **У завершених сесіях і в `past`-перегляді смужок немає.**
- CSS (`styles.css` ~24608): висота = `28px · var(--stim)` (мін. 3px), колір = змішування `--c-f0714f` (корал) і акценту за `--fat`.
  Той самий `--fat` ужито в `.gw-bar` («цінність наступного сету»).

### 2.2 Що рахується (`SessionView.rowMeters`, рядок ~1325)

Для вправи беруться `priorBefore(ex)` (скільки «жорстких сетів» цільовий м'яз мав до початку цієї вправи) і
`ref = workingKg(ex.sets)` (**максимальна вага серед усіх не-розминкових сетів вправи, включно з майбутніми**).

| Тип сету | висота `--stim`                                                                                                                                                     | колір `--fat`                                                                                                                    |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| розминка | `1 − load`, де `load = min(1, prior / plateau)`, `prior` = `priorBefore` + Σ `setHardness` попередніх сетів цієї вправи, `plateau` = 11 (персоналізований 8,5…14,5) | `load`                                                                                                                           |
| робочий  | `setStimuli`: `marginalStimulus(prior, plateau) · setHardness(s)`                                                                                                   | `min(1, max(drop / 0,1; 1 − stim))`, де `drop` = `performanceDrops` (втрата e1RM відносно найкращого попереднього робочого сету) |

- `setHardness` робочого: failure → 1; `rpe ?? rpeAuto`: ≥7 → 1, ≥6 → 0,5, інакше 0,25; без оцінки → 1.
- `setHardness` розминки: кусково-лінійна за RIR, де RIR оцінюється Epley від `workKg` в припущенні «робочий сет = 10 повторів
  до відмови»; **якщо робочого сету ще немає (`workKg = 0`) — константа 0,05** (`WARMUP_UNKNOWN_HARDNESS`).
- `marginalStimulus(prior) = 1 / (1 + (prior / 6)²)` (за замовчуванням плато): 1 → 0,5 при 6 сетах → ~0,26 при 10.
- `priorBefore(ex)` = `muscleTally(попередні вправи) + carry(primary)`; «попередні» = вправи з `firstAt(e) < firstAt(ex)`,
  де `firstAt` = мінімальний `loggedAt` серед сетів вправи (**порівнюється час першого сету вправи, а не час кожного сету**).
  `muscleTally` додає `setHardness` (зі своїм `workingKg` кожної вправи) для первинного м'яза і ×0,5 для вторинних.
- `carry` = `carryOverSets(finished, workoutStart)`: для кожної завершеної сесії за 16 днів доза (кількість сетів м'яза, вторинні ×0,5,
  **розминки рахуються як повні сети**, бо `muscleWorkInWorkout` бере `e.sets.length`) лінійно спадає до 0 за вікно
  `RECOVERY_DAYS[м'яз] · clamp(доза/(MAV·0,5), 0,7…1,6) / readinessMult` і множиться на `CARRY_WEIGHT = 0,5`.
  Це одиниці «жорстких сетів», які **додаються до лічильника стимулу**, а не окрема «готовність».

### 2.3 Дефекти (відтворення за кодом)

Числа нижче — розрахунок за поточним кодом, не вимірювання в браузері (синтетичні сети, свіжий м'яз, `carry = 0`).

1. **Розминки 8×60, 8×100, 8×130 перед 5×150 (RPE ~6).**
   Поки робочого сету ще немає, `workKg = 0` і кожна розминка важить 0,05: смужки 1,000 → 0,995 → 0,991.
   Після логування 5×150 `workKg = 150` і **усі смужки розминок перераховуються заднім числом**: жорсткості 0 / 0 / 0,082, смужки
   1,000 / 1,000 / 1,000, а робочий сет стрибає до `stim = 0,9998 · 0,5 = 0,50`. Тобто (і) розминки нерозрізнювані,
   (ii) вигляд минулих сетів залежить від майбутніх, (iii) на межі розминка→робочий стрибок 1,00→0,50 без фізичної причини.
2. **«Друге дихання» (15×40 розминка → 8×60 RPE ~6 → 8×60 RPE ~7,5 з відпочинком 0:59 і 0:26).**
   Розминка: жорсткість 0 (RIR 15 за Epley від `workKg = 60`), смужка 1,00. Другий сет: `1 · 0,5 = 0,50` (RPE 6 → жорсткість 0,5).
   Третій сет: `prior = 0,5`, `marginalStimulus = 0,993`, RPE 7,5 → жорсткість 1 → **0,99**. Смужка «наповнилась» з 0,50 до 0,99
   лише тому, що змінилась оцінка зусилля цього ж сету, при відпочинку 26 с. Причина — висота працює як «цінність сету для росту»
   (залежить від власного RPE сету), а не як стан м'яза; відпочинок не входить у формулу взагалі.
3. **Відпочинок ігнорується скрізь.** `loggedAt`, `restSec`, `restBeforeSetInWorkout` читаються тільки для підпису «відпочинок 0:59»
   (рядок ~3667); у `stimulus.ts` відпочинку немає.
4. **Дроп-сети.** `setHardness`, `performanceDrops` (`e1`), `setStimuli` дивляться лише на `s.weight`/`s.reps`; `s.drops` (`DropEntry[]`)
   ігнорується: сет з трьома дропами важить стільки, скільки його перша частина. `reverse-drop` і `static-dynamic` проходять як звичайні
   робочі (для `static-dynamic` ваги немає → `performanceDrops` його пропускає, `setHardness` = 1).
5. **Суперсети/кола.** «Раніше» визначається за часом першого сету вправи: при A1 B1 A2 B2 вправа B бачить **обидва** сети A (також A2,
   зроблений після B1), а вправа A не бачить жодного сету B. Реальний порядок по сетах (`loggedAt`) не використовується.
6. **Дві різні шкали на одній смужці:** розминка = «залишок» (`1 − load`), робочий = «внесок у ріст». Тому на переході смужка стрибає
   (пп. 1–2). Колір = гірше з «спад продуктивності ≥10 %» і «низький стимул» — теж суміш двох понять.
7. **Старт дня.** Для м'яза, тренованого вчора, `carry` піднімає `prior` одразу (приклад: груди вчора, 12 сетів, 1 доба, MAV 14:
   вікно `2,5 · 1,6 = 4,0` д, `carry = 12 · 0,75 · 0,5 = 4,5` → перший робочий сет вже `marginalStimulus(4,5) = 0,64`, а розминка `1 − 4,5/11 = 0,59`).
   Це змішує «втому» і «спадну віддачу росту» в одному числі.

## 4. Що з джерел випливає для моделі

1. **Монотонність відновлення в межах хвилин.** Ресинтез PCr — спадна експонента з напівчасом ~20–60 с (№1) і не має «перельоту»
   над рівнем до навантаження. Єдиний відомий механізм поліпшення результату за хвилини — постактиваційна потенціація після важких
   скорочень (№30, вторинне джерело) — до нашої смужки не стосується (розминка лише допомагає, і ми її не моделюємо).
   Висновок: «друге дихання» у сценарії B (смужка 0,50 → 0,99 за 26 с) фізіологічно не існує; це артефакт формули.
2. **Відпочинок суттєвий і не вичерпується 1–2 хв.** Повтори по сетах падають навіть за 2 хв (№3), 5 хв дає на ~46 % більше повторів,
   ніж 1 хв (№5, №4), довгий відпочинок зберігає якість сетів і дає кращі результати у тренованих (№6). Тобто відновлюваної частки
   втрати має бути **велика, але не 100 %**, а вузька швидка компонента (напівчас ≈ 1 хв) не пояснює все (бажаний `h` у верхній межі
   40–60 с діапазону PCr). Числових даних «повтори в сеті N при відпочинку R» у отриманих текстах немає — калібрування чисел
   лише якісне (див. §6 і план калібрування в specs).
3. **Близькість до відмови нелінійно визначає втому.** До відмови — відновлення 48–72 год; не до відмови з тим самим сумарним
   числом повторів — 6 год (№15); втрата швидкості 20 % vs 40 % дає майже той самий приріст сили при ~40 % менше повторів (№14).
   Підстава взяти вартість сету зростаючою **швидше за лінійно** від «частки використаного запасу повторів». Показник степеня не
   виміряний (припущення).
4. **Оцінка RIR/RPE шумна і зсунута.** Люди недооцінюють запас у середньому на ~1 повтор (№11) — справжній запас зазвичай трохи
   більший, ніж лог. Для моделі це означає: RPE — наближення, його похибка ~1 RIR; тому сети без RPE не відкидаємо, а рахуємо за
   e1RM, і не робимо різких порогів за RPE (як у старому `setHardness`: 5,9 → 0,25, 6,0 → 0,5, 7,0 → 1).
5. **e1RM лише зі сетів цієї ж вправи.** Повторів до відмови на заданому %1RM відрізняється між вправами (№28) і людьми (№27;
   розкид 2–4× на 70 %), тож будь-яка «універсальна» таблиця (в т.ч. припущення «робочий сет = 10 повторів до відмови» з
   `warmup-fatigue.md`) гірша за e1RM, виведений із власних залогованих сетів вправи **з урахуванням RPE/RIR**: сет 5×150 при RPE 6
   дає e1RM = 150·(1 + (5+4)/30) = 195, а не 150·(1+5/30) = 175 (як у `setBestE1rm`, що вважає кожен сет «до відмови»). Формула Epley
   залишається наближенням, надійнішим у діапазоні до ~10 повторів (так і обмежує `store.est1rm`).
6. **Обсяг за сесію.** Віддача спадна; «точка непомітної переваги» ≈ 11 фракційних сетів (препринт, №20). Це про **ріст**, а не про
   те, скільки м'яз може віддати в наступному сеті, тому смужка-бак це число не використовує (плато лишається для «цінності сету»,
   `marginalStimulus`, `tiredVerdict`).
7. **Міжсесійне відновлення не дорівнює лінійному «відсотку».** Показники продуктивності відновлюються швидше й залежать від
   близькості до відмови та об'єму (№15, №16), ушкодження — довше й залежить від досвіду (№18), вправа на одному суглобі відновлюється
   довше за багатосуглобову (№17, слабке джерело). Через 24 год після важкого «об'ємного» присіду у тренованих CMJ −9,6 %, момент
   у ізокінетиці до −20 % (№16, суперечливо в тексті).
8. **Дроп-сети.** Довгострокових переваг для гіпертрофії при зрівняному обсязі не виявлено (№26); про гостру втому в доступних мені
   джерелах чисел немає (№25 не відкрито). Тож дроп-сет моделюємо за визначенням (кожен сегмент — підхід до відмови без відпочинку),
   без джерельного числа.
9. **Суперсети.** Антагоністична пара зберігає об'єм за хвилину ефективніше й не гірша за традиційну за об'ємом (№22, №23, №24);
   для «схожих» м'язів об'єм падає (№24). Для бака це означає: втрата тієї ж групи в парі не відновлюється «між» її сетами, а
   відпочинок цього м'яза = реальний час між двома його сетами (включно з роботою партнерської вправи) — тому відліковуємо відпочинок
   **по м'язу**, за часовими мітками сетів.

## 5. Чи надійний «відсоток відновлення» у `recovery.ts`

Як рахується: `muscleReadiness` бере **останню** сесію за 16 днів, де м'яз отримав роботу; `daysSince = (now − startedAt)/доба`;
доза = кількість сетів м'яза в тій сесії (первинні ×1, вторинні ×0,5; **розминки як повні сети**); вікно
`effDays = RECOVERY_DAYS[м'яз] · clamp(доза/(MAV·0,5), 0,7…1,6) / readinessMult(at)`; `readiness = clamp(daysSince/effDays + boost·0,12, 0, 1)`.
`RECOVERY_DAYS` — 1,5–3 доби за м'язом.

Оцінка:

- **Форма.** Лінійна рампа від 0 до 1 — спрощення. Для показників продуктивності (CMJ, швидкість) відновлення швидше й нелінійне
  (№15, №16). Як «відсоток відновлення м'яза» для користувача — прийнятно; як «частка втраченої продуктивності» — ні:
  вчорашні груди з дозою 12 мають `readiness = 0,25`, тоді як виміряний дефіцит продуктивності через добу ~10–20 % (№16).
  Тому в моделі бака використовується **зважене** `T₀ = 1 − λ·(1 − readiness)`, `λ = 0,25` (див. spec).
- **Лише остання сесія.** Дві сесії поспіль (пн важка, вт легка) → середа читає лише вівторок. `carryOverSets` суму всіх сесій
  враховує, `muscleReadiness` — ні (розбіжність між двома механізмами одного застосунку).
- **Доза не знає інтенсивності.** Розминки, легкі сети й сети до відмови важать однаково; №15 показує різницю 6 год vs 72 год.
- **Вікна — практична евристика** (RP/Israetel, див. коментар у `loadWindow.ts`), не рецензована; №18 каже, що вікна залежать
  від досвіду (повторний бій), а в моделі вони сталі.
- **`boost` +0,12 і `readinessMult`** (нікотин/алкоголь) — глобальний стан поза сесією: для детермінованого перегляду минулої сесії
  їх треба фіксувати на момент початку тренування; бак передбачає `boost = 0` (рішення для людини, див. spec).
- **Висновок:** число придатне як **вхід** (початкова точка бака для першого сету дня) зі зниженою вагою `λ`, але не як точна
  фізіологія. Виправляти `recovery.ts` у цій задачі не пропонуємо (споживачі: readiness-коуч, picker, віджети).

## 6. Чесні обмеження

- Жодне джерело не вимірює «бак для вправи» напряму. Модель — інженерний синтез: напівчас PCr (№1), якісні ефекти відпочинку (№3–6),
  нелінійність близькості до відмови (№14, №15), шум RIR (№11).
- Параметри `φ` (частка відновлюваної втрати), `C_FAIL` (вартість сету до відмови), `p` (степінь), `λ`, а також `RIR` за
  замовчуванням для сетів без оцінки — **припущення без джерела**; діапазони чутливості — у `specs/set-bars-tank.md`.
- Більшість доказів — чоловіки 20–30 років, присід/жим; жінки, літні, ізоляційні вправи, тренажери — екстраполяція.
- Хвилинні відновлення в №3–5 виміряно як повтори, а не як «готовність м'яза»; ми ототожнюємо ці поняття.
- Ефект потенціації (PAPE), кардіо/центральна втома, кофеїн, сон — не моделюємо.
- №20 — препринт; число 11 у коді має ту саму надійність.
- Помилки в завданні, які я знайшов: «McLester 2003» → у реальності 2000 (№19); «Hickmott 2022» не про точність RIR (№12) —
  для цього тут Halperin 2021/22 (№11).

## 7. План калібрування (після першої версії)

Беклог, не вимога першої партії: на синтетичних/власних (із дозволу) логах підібрати `φ`, `C_FAIL`, `p` мінімізацією похибки
прогнозу «повтори наступного сету при тій самій вазі = повтори попереднього · (T_наступний / T_попередній)» для сетів до відмови з
відпочинком ≥ 30 с. Дані — лише існуючі поля (`loggedAt`, `reps`, `weight`, `rpe`, `restSec`); прод-БД лише для читання, без
запису. Поки калібрування немає, параметри заморожені (правило змін у spec).
