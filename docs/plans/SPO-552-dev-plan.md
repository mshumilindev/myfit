# SPO-552: повний план розробки планувальника (11.11.2026)

Статус: **план затверджено власником 11.11.2026 (19:12), розробка дозволена.** `cpd` лише за окремою командою.

## 0. Рішення власника 11.11 (19:12), чинні понад усе нижче

1. Назва аддона: **Planner** (id `planner`).
2. Аддон видалено → availability тренеру **не показується**. У основному бандлі **нічого** про Planner, лише стаби там, де йдуть підрахунки (як для Health: маска/фасад `plannerRt` з нейтральними значеннями); увесь код у ледачому чанку `plannerBoot`, що вантажиться лише поки аддон встановлено. Дані в БД зберігаємо, повторне встановлення їх повертає.
3. macOS: Spotter **живе в menu bar**, закриття вікна не завершує застосунок; **один раз** показує повідомлення «додайте Spotter в автозапуск» (прапор «показано» зберігається, повтор лише за явною дією в налаштуваннях).
4. Запис у журнал згод для availability: так. Юриста не чекаємо: Claude сам оновлює згоди, Privacy Policy, Terms коли новий контент цього потребує (правило додано в `legal-compliance.md`); `{{ЮРИСТ}}` лишається лише для фактів, які не можна вигадувати.
5. Dismiss у стані «asked» не потрібен: тренер бачить availability лише коли клієнт дав згоду.

Джерела: `SPO-552-planner-spike-2026-11-11.md` (S), `...-addendum-2026-11-11.md` (A1), `...-addendum-2-desktop-2026-11-11.md` (A2), `SPO-552-legal-changes-2026-11-11.md` (L), затверджений дизайн, рішення власника 11.11. Де нижче інакше, ніж у S/A1/A2, чинне нижче (розділ 1).

## 4. Дані й безпека

Колекції (рішення S п.3 + A1-A, без змін): `users/{uid}/planner/events/{id}` (запечатано `sealDoc`: назва, нотатка, іконка, колір, правило повтору, тривалість, lead, зона, based-on ref; відкрито лише `id` UUID, `mode`, `nextFireAt`, `enabled`, `v`, мітки часу); `planner/alerts/{id_start}` (відкритий стан: `state`, `snoozeUntil`, `by`, `rev`, `updatedAt`; видаляється після розв'язання і через 6 год після `nextFireAt`); `planner/state` (`enabled`). Нове з рішень власника:

- `planner/availability` (запечатано: тижневі діапазони). Відкритого нічого, окрім `v`, `updatedAt`.
- **Публікація для тренера:** вільні/зайняті інтервали (без причин) як **окремий документ за схемою наявних share-документів**, шифрований ECDH-грантом на тренера лише після Allow, відкликається видаленням гранта (як інші категорії `shareModel`; повторно використати `vaultGrants`/`vaultShare`, нових криптопримітивів не вводити). Зайнятість із Health (Unwell/Full rest) потрапляє як «busy» без причини.
- Запит тренера: запис у наявній колекції запитів доступу (`AccessAskCard`/`accessAsk.ts`) з новим `ShareId` `availability`; статуси off / asked / full.
- Rules (`firestore.rules`): `planner/**` читає й пише лише власник; публікація availability читається лише тренером із грантом; тести rules для обох. Колекції в `autoMigrate`, round-trip тест, тест «немає plaintext».
- Реєстр даних: рядки «Графік нагадувань» (шифровано, лише власник) і «Доступність» (шифровано, тренеру за згодою, free/busy). Експорт N6 включає обидва розшифрованими на пристрої; каскад видалення акаунта прибирає `planner/*`, публікацію availability і Cloud Tasks.
- Вимкнення аддона: `planner/state.enabled=false`, дані не чіпаємо. Публікація availability тренеру при вимкненому аддоні **призупиняється** (тренер бачить «Not shared»), гранти не знищуються; питання власнику (розд. 11, №2).
- Пристрій: локальна копія лише запечатана (`offline/`), чиститься `deviceWipe`; нові ключі в `localKeys.registry`.
- Cloud Task несе лише `uid`, `id`, `dueAt` (A1).

## 5. Сервер (functions)

Новий `functions/src/planner*.ts`: тригер на запис події → Cloud Task на `nextFireAt − lead`; спрацювання перечитує подію, `state`, `alerts`; `sendToUser` з `kind:'planner'` або `'planner-ring'`, `text:'planner'` (ключ у `coach/pushText.ts` у 5 локалях, паритет-тест); окремий лічильник від `REMINDERS_PER_DAY`; `shouldDeliver` отримує `planner-ring` (ігнорує тихі години за дефолтом події); повтори `ring` (початково 2 хв, до 5 разів, константи з тестом, уточнити після тесту на пристрої); snooze через Cloud Task на `snoozeUntil`; наступне входження серії планується одразу (ідемпотентний id таска). `sw-push.js`: гілка `planner-ring` (`tag`, `renotify`, `requireInteraction`, `vibrate`, на Safari/iOS опції ігноруються).

## 6. Десктоп (Electron) і трей / menu bar

- Міст лише додаванням: `scheduleAlarms(list)`, `cancelAlarms(ids)` (id, момент, режим; без назв), `setTray(state)`. Клієнт детектить наявність методів, старі оболонки працюють як PWA.
- Чиста логіка планування у `desktop/src/alarms.ts` без імпорту `electron` (підхід `hideWindow.ts`), юніт-тести.
- **Трей/menu bar:** Windows: наявний трей розширюється (меню «Up next», «Open Spotter», «Quit»); macOS: menu bar `Tray` + `app.dock` поведінка; закриття вікна **не завершує** застосунок, коли ввімкнено «Show the icon» (зміна `closeBehavior`, SPO-277 переглянути й повідомити власника). Клік по іконці відкриває вікно. Меню несе лише локально розшифрований текст із запечатаної копії.
- Автозапуск `app.setLoginItemSettings`, перемикач «Start Spotter with my computer» (дефолт вимкнено).
- Дзвінок: Windows `timeoutType:'never'` + звук оболонки; macOS непідписаний (SPO-162): нативні сповіщення не доставляються, тож дзвінок = екран дзвінка у відкритому застосунку, меню в menu bar працює. Linux без гарантій.
- Залежності й реліз оболонки: SPO-159, SPO-162; нова версія мосту потребує релізу оболонки окремо від вебу (`desktop-shell.md`, `releases.md`).
- PoC (виконує власник на пристрої, нас не блокує): `getToken` у нашому Electron; стабільність таймерів основного процесу у треї; Windows `timeoutType:'never'` і Focus assist; macOS menu bar без підпису.
