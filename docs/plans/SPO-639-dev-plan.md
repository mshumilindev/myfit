## Вимір №1 (факт)

Hooks з `.claude/settings.json` у хмарному чаті проєкту **не виконуються** (`echo "hook-probe --no-verify"` пройшов, хоча скрипт напряму дає exit 2). Тому: інструкції + `wf` за правилом + CI/Linear-гейти + зовнішній цикл. Desktop, CLI, одно-репо хмара, доступ до Linear з hook, токени/вартість — **не виміряні** (блок L).

## Самі на собі (dogfooding, рішення 27.11 01:54)

Уся подальша розробка йде вже за новим воркфлоу, а не «потім»:

1. **Крок 0 — завантажити цей план у `wf`:** `wf start SPO-639`, далі кожен рядок таблиці блоків і кожна партія = пункт (`wf add`). Відтоді статус прогресу береться з `wf status`, а не з пам'яті чату.
2. **Бутстрап:** до готовності `wf` (партії A.1–A.3) стан веду тимчасово в таблиці задач і Linear-коментарі «Прогрес»; щойно `wf` працює — переношу всі пункти в нього й далі лише через нього.
3. **Правила для кожного пункту:** `doing` → зміна → доказ (`done --evidence`) → коміт локально; без доказу пункт не закривається. Блокери йдуть у пакет «Чекає на мене», робота триває з іншими пунктами.
4. **Доповнення власника посеред роботи** = `wf add` + рядок у плані + AC в Linear, без зупинки. Відсоток перераховується чесно (може впасти).
5. **Linear:** після кожної партії — оновлення закріпленого коментаря «Прогрес» і галочок AC; підзадачі в Triage створюються за цим планом (по одній на блок + «Тести: …»).
6. **Верифікатори (блок D)** підключаються до власної розробки одразу, щойно з'являються: перший блок, що пройде їх, — блок A.
7. **Метрики (блок H)** збираються з першого `wf start`: журнал подій без PII накопичується з самого початку, щоб було з чим порівнювати «до/після».

## Шар 1 (розробляємо зараз, T1): блок A

### Файли (лише нові, окрім одного рядка `.gitignore`)

- `scripts/wf.mjs` — тонкий CLI (парсинг argv, читання/запис стану).
- `scripts/lib/wf-core.mjs` — чисті функції: `reduce(state, event)`, `renderStatus(state)`, `progress(state)`, `validateEvent(event)`.
- `tests/wf.test.ts` — unit + CLI smoke у тимчасовій теці.
- `.gitignore` — рядок `.claude/state/` (стан сесії локальний).
- Не чіпаємо: `CLAUDE.md`, `.claude/settings.json`, `package.json`, lockfile, CI, `.githooks/`.

### Модель стану (`.claude/state/wf.json`, подієвий журнал `.claude/state/wf-events.jsonl`)

- Задача: `{ id, title, linear?, items: [{ id, text, kind: 'ac'|'step'|'extra', status: 'todo'|'doing'|'done'|'blocked', evidence?, ts }] , blocked: [{ item, reason, needs: 'design'|'cpd'|'decision'|'access', ts }] }`.
- Подія: `{ ts, type: 'start'|'add'|'doing'|'done'|'block'|'unblock'|'heartbeat', item?, category? }`. **Без тексту чату й без персональних даних**: лише id, категорії, час. Довільний `text` пункту плану зберігається у стані, не в журналі подій.
- `done` вимагає `--evidence "<команда/файл/посилання>"` (інваріант «не заявляй готово без доказу»); порожній доказ → відмова з кодом 2.
- `block` не зупиняє: пункт отримує `blocked`, а `status` показує пакет «Чекає на мене» окремим блоком.
- Лічильник без прогресу: `heartbeat` без нових `done` за N викликів → у `status` рядок «змінити підхід» (не stop).

3. `wf.mjs`: `start/add/doing/done/block/status`, файлове сховище, коди виходу; CLI smoke-тест у tmp-теці.

4. **Ролі додатка (member/trainer/manager/нутріціолог/admin):** функція не змінює продукт; ролі застосунку нічого не бачать. Роль «власник/PO» бачить `wf status`, пакет «Чекає на мене», картку результату; «Claude-агент» створює/позначає пункти; «верифікатор» читає й повертає вердикт, не пише код.

## Тести (матриця)

- Unit (`tests/wf.test.ts`): reducer, прогрес %, валідація подій, відмова `done` без доказу, `block` не змінює інших, детермінізм `renderStatus`.
- CLI smoke: `start → add → doing → done → status` у tmp-теці, коди виходу, відсутній стан = зрозуміле повідомлення.
- Guard: журнал подій не містить тексту й доказів.
- Мутаційні перевірки (вручну на A): інвертувати умову `done` без доказу — тест має падати (revert-check).
- Незалежне рев'ю: верифікатор «scope & diff» + «test quality» (D), бо інструмент впливає на дисципліну всіх чатів.
