## Архітектура (чернетка, перевірити)

1. Планова функція раз на добу тягне межі з дозволеного джерела, валідує, пише версію в Firestore (журнал) і публікує GeoJSON у Cloudflare KV через API.
2. Worker читає KV з кешем у пам'яті ізоляту на ~5 хв. Порожній або биті дані: fail-open (рішення 30.10), без блокування.
3. Звільнення території = нова версія без цього полігона; Worker підхоплює за ~5 хв, без релізу.
4. До дозволу джерела: ручне версіоноване завантаження того ж запису (власні межі власника), той самий код читання.

## Статус: на паузі (31.10)

Власник поставив на паузу до схвалення DeepState; задача в Backlog. Код синку (`occupiedSync*.ts`, 21 тест) готовий і лежить у гілці `spo-408-sync` (не в `main`, бо функція вимагає секрет `CLOUDFLARE_KV_TOKEN` до деплою). Worker уже читає KV, а без KV лишається fail-open.

## Блокери (стан 31.10)

- Джерело: власник дозволив DeepState/ISW (31.10). Це не дозвіл правовласника: ліцензія DeepState вимагає схвалення для комерційного API (заявка: https://api.deepstatemap.live/request), заборонено проксіювати API третім особам, потрібна атрибуція. Формат відповіді API не перевірено до отримання доступу. Конвеєр джерело-агностичний: `OCCUPIED_SOURCE_URL` + `OCCUPIED_NAME_PATTERN`; без URL функція нічого не робить.
- Секрет Cloudflare API для запису в KV (власник): кроки нижче.
- Юрист: власник 31.10 зняв блокер («можна чекати без нього»); `{{ЮРИСТ}}` у тексті варіанта B і вичитка lt/et лишаються позначеними, не блокують.

## Namespace (рішення)

Окремий KV namespace `spotter-geo-areas` (тільки межі; нічого іншого). Ключ `occupied-geojson` читає Worker (binding `OCCUPIED_KV`), пише лише функція `syncOccupiedAreas`. Токен має право лише на KV цього акаунта: Worker читає через binding, токен йому не потрібен. Журнал версій (дата, хеш, статистика, відхилення) у Firestore `system/occupiedAreas/versions`, не в KV.

## Кроки для власника

1. Подати заявку на доступ: https://api.deepstatemap.live/request (комерційне використання, мета: геообмеження за законом). Без схвалення джерело не вмикаємо.
2. Cloudflare Dashboard → My Profile → API Tokens → Create Token → Custom token: Account · Workers KV Storage · Edit; Account Resources: лише ваш акаунт; без IP-обмежень, TTL за бажанням. Скопіювати токен (показується один раз).
3. Account ID: Dashboard → Workers & Pages → праворуч «Account ID».
4. Namespace: `cd edge/geo-block && npx wrangler kv namespace create spotter-geo-areas`; id із виводу вписати в `wrangler.toml` (розкоментувати `[[kv_namespaces]]`, binding `OCCUPIED_KV`).
5. Секрет у Firebase (вводите самі, я його не бачу): `firebase functions:secrets:set CLOUDFLARE_KV_TOKEN`. Секрет має існувати до деплою функцій, інакше деплой `syncOccupiedAreas` впаде.
6. Параметри функції (не секрети): `OCCUPIED_SOURCE_URL`, `CLOUDFLARE_ACCOUNT_ID`, `OCCUPIED_KV_NAMESPACE_ID`, за потреби `OCCUPIED_NAME_PATTERN` (у `functions/.env.<project>`).
7. Після схвалення джерела: перший запуск функції вручну, перевірити запис у журналі та значення в KV, лише потім `wrangler deploy` Worker.

## Відкрите

- Реєстр процесорів/політика: нове вихідне з'єднання функції до джерела меж і до Cloudflare API (дані користувачів не передаються); запис у реєстр і політику робиться разом із підключенням джерела (`{{ЮРИСТ}}` на формулювання).
- Реальний формат API DeepState і точність `request.cf.latitude/longitude` перевіряються після доступу.
- Окремі підзадачі SPO-408.1–6 у Linear ще не створені.
