# SPO-225 · план розробки: відновлення пароля листом

Джерела: спайк SPO-215 (`claude/SPO-215-email-auth-decision.md` §5, §9), дизайн SPO-223 (6 екранів застосунку + 4 листи, затверджено власником 31.10), рішення власника 31.10: усі листи з одного відправника (Resend, SPO-426).

## Відхилення від спайка (пояснення)

Спайк пропонував віддати пароль Firebase Auth. У SPO-224/283 пароль лишився в нашому bcrypt (`credentials`), тож і скидання йде нашим: одноразове посилання (`invites`, `kind: reset`) → `claim` ставить `credentials/{uid}`, відкликає токени й passkeys. Це **той самий шлях, що вже працює для скидання адміном**, а не друга система. Пункт AC «міграція наявних користувачів» **знято цим рішенням**: пароль нікуди не мігрує, акаунти, ключі й офлайн-дані не змінюються, відкат не потрібен (нічого не ввімкнено окремим прапорцем). Рішення відображено в Linear-коментарі.

## Дані й безпека

`requestPasswordReset` (публічний callable): ліміт за IP (відомий відповіддю) і за адресою (прихований), пауза в індексі `emails` (`resetAt`, транзакція), лише підтверджена адреса + `status: active`; `claim` для `reset` не міняє статус (заблокований не відновлюється). Нових колекцій і rules немає; реєстр даних п. 11. Каскад видалення знищує нові лічильники (тест).
