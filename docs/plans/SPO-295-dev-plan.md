## 5. Дані, безпека, i18n (наскрізно)

- `consentRecords` (`users/{uid}/consentRecords/{id}`, не плутати з `consentLog` — історія згод на доступ тренера): append-only, власник лише читає, пише **тільки** callable `recordConsent` (час сервера); види: `terms`, `policy-ack`, `age-18`, `health:<feature>`, `atlas-ai`, `atlas-puter`, `geo-search`, `trainer-terms`. Угода (terms) і ознайомлення з політикою (policy-ack) — окремі записи, кожен з `version`, `textHash` (64-hex, для grant цих двох обов'язковий) і `at` (час запису; і для відкликань). Сервер не довіряє клієнту: grant приймається лише для **поточної** версії (`RELEASED_VERSIONS`, поточна = найновіша), відкликання — для будь-якої випущеної; видалений/заблокований акаунт запису не створює; повтор того самого стану — no-op (повертає наявний запис); ліміт нових записів на людину; `at` суворо зростає в межах виду. Id запису непрозорий (час + випадкове, без виду).
- **Відкрите питання власнику/юристу (S6):** `kind` лежить у документі відкритим текстом, тож за самим фактом запису `health:*` видно, що людина ввімкнула функцію здоров'я (навіть при непрозорому id). Запечатати це серверним шифруванням (DEK з `VAULT_MASTER` на сервері) не робимо в межах SPO-296: колекція пишеться лише сервером, а ротація ключа (`vaultMigrate`) переписує колекції з клієнта, тож запечатані сервером записи не можна перезапечатати без окремого механізму; також потрібні запис у реєстрі/експорті/каскаді видалення. Рішення: лишити відкритим, зафіксувати в реєстрі даних (R-рядок) і в Privacy Policy як метадані згод; власник/юрист вирішує, чи потрібне запечатування (тоді — окрема задача: серверний seal + клієнтський open + ротація).
- «Обов'язкові» = `terms`, `policy-ack`, `age-18`: відкликання = видалення акаунта (3-крокове, з копією даних перед видаленням). Решта — функціональні: відкликання вимикає функцію й пропонує видалити пов'язані дані.
- Rules: тести емулятором для кожної нової колекції/поля; нічого відкритим текстом у `localStorage` (SPO-216).
- Видалення: Firestore + Storage + кеші + `localStorage` + IndexedDB; тест «після видалення реєстр порожній» — частина AC SPO-285.
- i18n: ключі в `client/src/i18n/` (en, uk, pl); тексти документів — окремі словники з версією; політика обирає мову з перемикача застосунку (`LanguageSelector`).
- Дата «Last updated» у документах — генерується з версії.

## 11a. Рішення: gate і «не вдалося перевірити згоди» (власник, 22.10.2026)

Правило власника: без прийнятих Terms + Privacy Policy (і обов'язкових згод age-18) застосунок після входу непридатний. Стани `useLegalGate()`:

- `needed` (сервер підтвердив: згоди немає / відкликана / застаріла) — блокуючий аркуш 1, як і раніше.
- `clear` — записи, що є, задовольняють gate.
- **Не вдалося перевірити (завантаження / офлайн / помилка слухача) — залежить від кешу на пристрої:**
  - на цьому пристрої для цього uid **раніше було серверно підтверджено «clear» для поточних версій документів** (`spotter.consentVerified`: uid → `kind@version` обов'язкових згод; лише види й версії, пристроєвий ключ, лишається після виходу, прибирається при видаленні акаунта) → `unknown`: **fail open**, застосунок працює (offline-first, інваріант 2);
  - такого підтвердження **ніколи не було** (перший запуск офлайн, новий пристрій, піднята версія документа, очищене сховище) → `unverified`: блокуючий екран «Підключіться, щоб продовжити» (`LegalGateUnverified`) з «Вийти» / «Видалити акаунт»; онлайн під час завантаження той самий аркуш пише «Перевіряємо…» і зникає, щойно відповідає сервер.
- Прапорець ставиться лише коли сервер відповів «clear» (не з кешу), знімається, коли сервер каже `needed`. Підняття `LEGAL_VERSIONS` скидає fail-open для всіх: офлайн-користувач побачить екран підключення до першої серверної відповіді.
- Не блокують: необов'язкові згоди (drawer 2: невибране лише вимикає функції), публічні сторінки `/privacy` `/terms` (на них застосунку немає, повернення відкриває gate), екран запрошення `#/join/…` (тепер App слухає `hashchange` і для нього, тож застосунок не лишається відкритим під виключенням gate).
- Обмеження: gate клієнтський; Firestore rules / функції не вимагають згод (питання власнику: чи робити серверний enforcement).
