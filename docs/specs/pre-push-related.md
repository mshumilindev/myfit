# Швидший pre-push: кореневі тести лише зачеплені — spec

Задача: SPO-270 · Статус: у роботі · Власник: Mykola · 20.10.2026

## Мета і контекст

Pre-push ≈4 хв; найдовший крок — кореневий `npm run test:coverage` (`tests/**`, 500+ тестів ≈3 хв). Той самий набір із порогами 90/70/90/90 щоразу біжить у CI (`Unit tests + coverage gate`), тому локально достатньо тестів, зачеплених push-ом.

## Поза скоупом

Клієнтські тести (вже `client-tests-changed`), пороги покриття, склад CI.

## AC

- [ ] `scripts/root-tests-related.mjs`: diff від бази → `vitest related`; зміна конфігів/залежностей/setup → повний набір з coverage · доказ: `tests/rootTestsRelated.test.ts`
- [ ] `.githooks/pre-push` викликає скрипт замість `test:coverage`; повний гейт і пороги в CI без змін · доказ: diff + CI зелений
- [ ] Типовий push швидший на ≥1,5 хв · доказ: замір до/після
- [ ] ADR 008 + рядок у `.claude/rules/tests.md`

## Підхід

Аналог: `scripts/patch-coverage.mjs --run` (related-тести для клієнта). Рекомендовано: `vitest related <змінені файли>` у корені. Зміна `vitest.config.ts`, `tests/setup.ts`, `package*.json`, `tsconfig*.json` → повний набір із coverage (як у CI).
Альтернативи: (1) лишити повний набір — повільно, нічого не втрачаємо; (2) `--changed` за git — не бачить транзитивних імпортів так добре, як `related`.

## Вплив

UI/дані/безпека/i18n — немає. CI не змінюється: повний гейт там. Ризик: локально зелений pre-push не гарантує зелений кореневий гейт CI (це й так було для 8 клієнтських шардів).

## План тестів

Юніт: вибір режиму (`skip`/`related`/`all`). Замір: прогін на реальному diff.

## Реліз і відкат

Відкат: повернути `npm run --silent test:coverage` у `.githooks/pre-push`.
