# SPO-639 W21: надійний запис подій розробки (кожен чих, стабільно)

Вимога власника (28.11, 00:19): дашборд має сенс лише тоді, коли записується буквально кожна подія і записується стабільно. Тут: архітектура, що це гарантує, і як ми доводимо гарантію.

## 0. Принцип
Запис не «ламається тихо». Кожен шар або пише, або **шумно** повідомляє, що не зміг; повнота перевіряється незалежним джерелом (транскрипт сесії), а не довірою до самого запису. Дашборд показує «здоровʼя запису» як перший показник; червоний = дані ненадійні, і це видно одразу.

## 1. Що саме пишемо (повний перелік подій)
Один рекордер на **всі** hook-події Claude Code: `SessionStart`, `UserPromptSubmit`, `PreToolUse`, `PostToolUse`, `Stop`, `SubagentStop`, `PreCompact`, `SessionEnd`, `Notification`. Плюс події `wf` (add/doing/done/block/unblock/heartbeat/start) і блокування `guard-bash`. Плюс зріз git (коміти, гілки) у збирачі. Що в рядку: лише метадані (`ev, ts, sid, task, tool, ok, dur, cat, open, blocked, id, v`), без аргументів інструментів, без тексту промптів, без повідомлень комітів, без шляхів (R23).

## 2. Шари гарантії
1. **Запис (L1).** `scripts/lib/journal.mjs`: один виклик `appendFileSync` з прапором `a` (O_APPEND) на рядок ≤1 КБ; **файл на сесію** `.claude/state/journal/<sid>.ndjson` (нуль змагання між сесіями); `id` рядка = 8 байт random; fail-open: будь-яка помилка → exit 0, але помилка потрапляє в L2. Жодної мережі, жодних залежностей, лише `node:fs`/`node:crypto`, бюджет ≤40 мс.
2. **Запасні каталоги (L2).** Не вдалося записати в `.claude/state/journal` → `os.tmpdir()/spotter-journal` → `$HOME/.spotter-journal`; поруч `capture-errors.ndjson` (теж append, мінімальний рядок). Перший успішний каталог запамʼятовується в `journal-path`; збирач читає всі три.
3. **Самоперевірка при старті (L3).** `SessionStart`: (а) пробний запис і зчитування; (б) звірка `.claude/settings.json`: кожна обовʼязкова hook-подія має команду рекордера (інакше «recorder missing for <event>»); (в) лічильник `capture-errors` за останню добу. Будь-що не так → у контекст сесії друкується гучне «ЗАПИС ЗАХВОРІВ: …» і пункт `wf` `capture-fix` (needs: нічого, роби негайно).
4. **Парність подій (L4).** Інваріанти, які збирач перевіряє: кожен `PreToolUse` має `PostToolUse` з тим же `tool_use_id`, окрім перерваних (рядок `Stop`/`SessionEnd` після нього); `SessionStart` має `SessionEnd` або «тихий обрив»; кожен `UserPromptSubmit` має `Stop`. Порушення → подія `gap` у знімку, жовтий індикатор.
5. **Звірка з транскриптом (L5, незалежне джерело).** Hook отримує `transcript_path`; на `Stop`/`PreCompact`/`SessionEnd` рахуємо в транскрипті виклики інструментів і повідомлення користувача й порівнюємо з журналом за сесію. Відхилення → `gap {missing:N}`; відсутні події **добудовуються** з транскрипту (`src:"backfill"`, лише ім'я інструмента, час, ok). Журнал перестає бути «довірений на слово»: повнота доводиться.
6. **Згортка в шарди (L6, довговічність і транспорт).** На `Stop`/`PreCompact`/`SessionEnd` рахується шард `docs/reviews/dash/<task>/<sid>.json`: агрегати (виклики інструментів по годинах і по іменах), **усі** паузи, нуджі, компакції, блокування, wf-події, `gap` і стан здоровʼя. Шард детермінований (ті самі події → той самий байтовий вивід), тож повторний запуск нічого не дублює (ідемпотентно, злиття за `id`). Різні сесії → різні файли → git-конфліктів немає. Шарди відстежувані й їдуть із комітами до машини власника.
7. **Читання (L7).** Збирач дашборда: локальні журнали (живе, якщо сесія йде на цій машині) + шарди з git (хмарні сесії, оновлюються при кожному коміті) + пряме опитування git/CI. Дашборд пише вік даних: «живе / знімок N хв тому».
8. **Енфорс енфорса (L8).** `wf-stop-hook` не дає завершити хід, якщо поточна сесія в стані `capture-degraded`; `cpd-preflight` падає, якщо шард застарів відносно HEAD чи є `gap` без пояснення; guard-тест перевіряє, що `settings.json` містить рекордер для кожної обовʼязкової події і що жоден hook скрипт не друкує в stdout журнальний шум.
9. **Обрив і пошкодження.** Читач толерантний: недописаний хвостовий рядок пропускається й рахується; невідомі `ev`/`v` зберігаються як є (вперед сумісність). Ротація: журнал >10 МБ → новий сегмент; старіше 30 днів чистить нічна гігієна (тільки локальні журнали; шарди лишаються).

## 3. Чесні обмеження
- Дані з хмарної сесії потрапляють на localhost власника з наступним комітом/бандлом, не миттєво. Дашборд це показує («знімок N хв тому»).
- Hook не виконується, якщо платформа вбила процес миттєво; цей випадок ловить L5 (транскрипт) і L4 (немає `Stop`).
- Не можна гарантувати подій, які платформа не віддає hook-ам; для них єдине джерело транскрипт, звідси L5.

## 4. Тести (докази стабільності)
Хаос-набір: 20 процесів × 200 одночасних записів → рівно 4000 валідних рядків; обрив запису (усічений хвіст) → решта читається, хвіст пораховано; каталог без прав → запасний шлях + запис у `capture-errors`; відсутній рекордер у `settings.json` → guard падає; відсутні Post/Stop → `gap`; усічений журнал проти транскрипту → `gap` і backfill; повтор згортки → той самий байтовий вивід; схема й PII (токен/email/шлях відхиляються); продуктивність: p95 запису <40 мс на CI (м'який поріг, окремо від pre-push); перемішаний порядок рядків → стабільний результат.
