## Мета і контекст

Ліва смужка рядка сету зараз змішує два поняття (розминка = «залишок», робочий = «внесок у ріст»), залежить від власного RPE сету,
перераховується заднім числом, ігнорує відпочинок, дропи й справжній порядок сетів у суперсетах (Д §2.3). Результат: розминки
нерозрізнювані, між розминкою та робочим сетом стрибок, а сет, зроблений за 26 с після попереднього, може показати «повний бак».
Рішення користувача: **одна семантика — «бак»**: залишкова готовність цільового м'яза для цієї вправи, монотонна в межах вправи,
частково відновлюється лише відпочинком. Бак — **новий чистий модуль `client/src/setTank.ts`**, який читають лише смужки;
усе, що рахує `stimulus.ts` для статистики, лишається як є.

## 1. Глосарій і точні визначення

- **Бак** `T ∈ [0,1]` — залишкова готовність цільового м'яза `m` давати повтори в цій вправі; 1 = свіжий, 0 = нічого. Це не «відсоток відновлення» і не «внесок у ріст».
- **Бак сету** `tank(s)` — бак м'яза `m = primary(вправа)` **в кінці** сету `s`: після відпочинку, храповика та вартості самого сету (рішення людини №1). Свіжий перший сет
  уже показує свою вартість. Додатково повертається `before(s)` — бак на початку сету (після відпочинку й храповика, до вартості); саме `before` монотонний і є входом для
  наступних сетів. **Висота смужки** `barHeight(s) = display(tank(s))` — окреме поняття відображення (§2, «Відображення»).
- **Подія** — один сегмент роботи м'яза. Сет вправи, що зачіпає `m`: вага `w_m = 1` для первинного, `0,5` для вторинного
  (`SECONDARY_SET_WEIGHT` у `store.ts`). Дроп/реверс-дроп сет розкладається на сегменти `[основна частина, ...drops]` у порядку виконання.
- **Швидкий дефіцит** `Df` — частина втрати бака, що відновлюється відпочинком; **повільний** `Ds` — що не відновлюється до кінця сесії.
  `T = 1 − Df − Ds`.
- **Відпочинок перед подією** `rest` (с) — час між завершенням попередньої події **того ж м'яза** та початком цієї: `(loggedAt_цієї − loggedAt_попередньої) − setWorkSeconds(цього)`,
  як `restBeforeSet` у `store.ts` (`setWorkSeconds = max(30, reps·3)`, `durationMin·60` для таймованих). Інші м'язи не рахуються: у суперсеті
  час партнерської вправи — відпочинок для цього м'яза.
- **Запас повторів** `RIR` та **частка використаного запасу** `u = reps / (reps + RIR) ∈ [0,1]`: 1 = до відмови.
- **e1RM-еталон** `E_ref(s)` — максимум із (a) `e1rmHist` вправи (кращий e1RM її залогованих сетів **до початку цієї сесії**, вікно 56 днів, інакше рекорд —
  як `liftReference`) і (b) e1RM попередніх за часом не-розминкових сетів цієї вправи сьогодні. Тільки з **власних** сетів вправи (Д№27–28).
- **e1RM сету** `setE1rm(set) = w·(1 + (reps + RIR)/30)` для не-розминкових сетів з `w > 0`, `reps ≤ 10` (як `E1RM_MAX_REPS`) і тип навантаження `weight`;
  інакше 0. На відміну від `setBestE1rm`, враховує запас повторів (сет 5×150 при RPE 6 → 195, а не 175).
- **Вхід готовності** `R_m ∈ [0,1]` — `muscleReadiness(finishedBefore, workoutStart, 0).get(m).readiness` (відсоток відновлення з `recovery.ts`, Д§5), рахує
  викликач; модуль отримує готове число.

## 2. Модель

Стан по м'язу: `(Df, Ds, T_prev)`. Події м'яза йдуть у порядку `loggedAt` (див. §4 про відсутні мітки).

**Старт.** `T₀ = 1 − λ·(1 − R_m)`; `Ds = 1 − T₀`, `Df = 0`, `T_prev = ∞`.

**Для кожної події `k` м'яза:**

1. Відновлення: `Df ← Df · 2^(−rest_k / h)` (перша подія: без змін; розрив ≥ 3 год або заминка в проміжку → `Df ← 0`, як у `restBeforeSet`).
2. Вільний рівень: `T_free = 1 − Df − Ds`.
3. **Храповик (немає «другого дихання», ревізія 2026-10-18):** `T_prev` = бак у **кінці** попередньої події цього м'яза (після її вартості); `T_k = min(T_prev, T_free)`; якщо спрацював — `Df ← 1 − T_k − Ds` (надлишок відновлення відкидається). Справжня перерва (розрив ≥ 3 год або заминка в проміжку) знімає храповик: `T_prev ← ∞`, `Df ← 0`. **Наслідок, який треба знати:** `T_free ≥ T_prev` завжди (відновлення лише додає), тож без справжньої перерви `T_k = T_prev` і відпочинок на бар **не впливає** — `h` і `φ` діють лише через перерву (там `Df` обнуляється, лишається `Ds`).
4. **Старт сету** `before = T_k`. Бар сету = рівень у кінці сету (після кроку 8 для всіх сегментів), див. «Відображення».
5. Близькість до відмови (для кожного сегмента, пріоритет джерел RIR):
   1. `failure ∈ {manual, auto}` або `partials > 0` → `RIR = 0`;
   2. `rpe` → `RIR = clamp(10 − rpe, 0, 5)`;
   3. `rpeAuto` (оцінка застосунку, `rpe.ts`) → так само;
   4. є `E_ref` і `w > 0` і тип навантаження `weight`: `RIR = max(0, 30·(E_ref/w − 1) − reps)` (Epley);
   5. розминка без еталона → `u = U_WARM_UNKNOWN`;
   6. інакше → `RIR = RIR_DEFAULT`.
      Дроп/реверс-дроп: останній сегмент — за правилами 1–3 (якщо нічого немає → `RIR = 0`, як у `failure.ts` «`drop`»); решта сегментів `RIR = RIR_SEG`.
      Сети на час (`static-dynamic`, `measure: hold|time`): `reps_eff = durationSec / 3` (`SET_SEC_PER_REP`), `w` ігнорується (правила 1–3, 6).
6. Вартість: `u = reps / (reps + RIR)`, `c = C_FAIL · u^p · w_m`.
7. Втрата: `loss = c · T_k` (частка **поточного** бака, тому `T ≥ 0` завжди).
8. Розподіл: `Df += φ·loss`, `Ds += (1 − φ)·loss`; `T_prev ← max(0, T_k − Σloss)` (бак у кінці події).
9. Після сету (причинність): якщо не розминка і `setE1rm > 0` → `E_ref ← max(E_ref, setE1rm)`.

Сегменти дропів: відпочинок між ними 0 (`Df` не відновлюється), храповик не застосовується всередині сету.

**Відображення (рішення людини №2).** Модель дає бак `T` (фізичний зміст, лінійний). Для екрана він перетворюється **безстанною, детермінованою, монотонною** функцією:

```
d = 1 − T                         // дефіцит, 0..1
display(T) = max(FLOOR, 1 − d^γ)   // γ = 0,5, FLOOR = 0,1
--stim = display(tank_у_кінці_сету)
--fat  = max( clamp((1 − T) / 0,8, 0, 1),  clamp(performanceDrop / dropTolerance, 0, 1) )
```

Колір береже наявний сигнал `performanceDrops()` (реальна виміряна втрата повторів відносно найкращого робочого сету; `dropTolerance` — особистий поріг вправи, типово 0,1) і додає втрату бака.
Розминки в `performanceDrops` не входять, тож їх колір = лише втрата бака.

_Чому не авто-діапазон за min/max (відхилено)._ Масштаб «від найнижчого до найвищого бака серед показаних сетів» змінював би висоту **вже намальованих** смужок, щойно новий сет розширює діапазон: це
рівно той дефект «минуле залежить від майбутнього» (research §2.3 п. 1(ii)), порушення причинності AC6, і воно ламається при видаленні/редагуванні сету; одне й те саме значення бака
мало б різну висоту на різних екранах і між сесіями. Безстанна функція від одного `T` цього не має.

_Чому `1 − d^γ`, γ = 0,5._ Користувач має читати **дефіцит**, а він живе в діапазоні 0,01…0,5 (розминка забирає ~1–10 %); у лінійній шкалі 28 px крок у 1 п.п. = 0,28 px, нижче порогу
розрізнення довжини (відносний поріг Вебера для довжин порядку 2–3 % — у нашому випадку ≈ 1 px; цифра з пам'яті, не перевірена в цій задачі — рівень C). Стислий степінь дефіциту
(γ < 1) розтягує малі значення. Закон Стівенса для довжини має показник ≈ 1, тобто це не «корекція сприйняття», а свідомий вибір відображення; γ = 0,5 — найпростіший стандартний
компресійний степінь (квадратний корінь — практика візуалізації для довгохвостих величин; для площ символів — компенсація Флеpері з показником ≈ 0,57, також з пам'яті, рівень C).
**γ — вибір дизайну, не виміряна величина**; вона не впливає на модель, лише на пікселі, і змінюється одним числом у `TANK_PARAMS` (з оновленням цієї таблиці).

| Бак `T`     | 0,99 | 0,95 | 0,90 | 0,80 | 0,60 | 0,40 | 0,20  | 0,00 |
| ----------- | ---- | ---- | ---- | ---- | ---- | ---- | ----- | ---- |
| γ = 0,33    | 0,78 | 0,63 | 0,53 | 0,41 | 0,26 | 0,16 | 0,10* | 0,10 |
| **γ = 0,5** | 0,90 | 0,78 | 0,68 | 0,55 | 0,37 | 0,23 | 0,11  | 0,10 |
| γ = 0,67    | 0,95 | 0,87 | 0,79 | 0,66 | 0,46 | 0,29 | 0,14  | 0,10 |

Побічний ефект (ціна): біля `T = 1` нахил найкрутіший — перші сети «спадають» візуально швидко; біля нуля різниці стискаються (під підлогою 0,1 ≈ 2,8 px сети не розрізнити; CSS-мінімум смужки 3 px).
Висоти двох прикладів зі скріншотів — у §3.1–3.2.

| `U_WARM_UNKNOWN`      | 0,15     | `u` розминки без еталона                          | **припущення (без джерела)**; ≈ `u` першого розминкового кроку (8×60 при e1RM 195 дає 0,12)                                                                                              |
| `FLOOR`, `γ`          | 0,1; 0,5 | підлога й степінь відображення (не модель)        | вибір дизайну (рішення людини №2), див. «Відображення»                                                                                                                                   |
| `TANK_RED`            | 0,8      | втрата бака, що фарбує смужку повністю            | вибір дизайну; 0,5 → 0,8 після рев'ю (при 0,5 колір насичувався за 2–3 сети)                                                                                                             |
| `REST_FALLBACK`       | 90 с     | відпочинок, коли мітки часу немає і `restSec` теж | **припущення (без джерела)**; типовий відпочинок між сетами                                                                                                                              |
| Прийняті з застосунку |          |                                                   | вторинний м'яз 0,5 (`SECONDARY_SET_WEIGHT`); Epley 30; `SET_SEC_PER_REP = 3`, `SET_MIN_WORK_SEC = 30`; `E1RM_MAX_REPS = 10`; розрив ≥ 3 год = повний відпочинок (`restBeforeSet`)        |

Вільних чисел п'ять (`h, φ, C_FAIL, p, λ`) плюс чотири умовні константи; `RIR_SEG = 1` і «останній сегмент дропу — до відмови» — прийняті людиною припущення (рішення №6).
Чутливість (бак у кінці: A сет 4 / B сет 3 / 5-й сет до відмови, 10 повторів): базові значення 0,622 / 0,465 / 0,055 (Python-репліка, збігається з кодом на базі).
Після ревізії храповика `h` і `φ` **не впливають** на бари в межах однієї перерви (відпочинок бар не піднімає), тому з таблиці вилучені; бак у кінці = `T₀ · Π(1 − C_FAIL·uᵖ·w)`.

| Зміна                | A сет 4       | B сет 3       | 5-й сет       |
| -------------------- | ------------- | ------------- | ------------- |
| `C_FAIL` 0,35 / 0,55 | 0,690 / 0,545 | 0,554 / 0,369 | 0,116 / 0,018 |
| `p` 1 / 2            | 0,480 / 0,725 | 0,376 / 0,545 | 0,055 / 0,055 |

Найчутливіший — `C_FAIL`; `p` зсуває лише сети далеко від відмови. 5 сетів до відмови поспіль дають 0,055 — підлога відображення, це наслідок вибору `C_FAIL`.

**Чому `muscleReadiness` без `boost`/алкоголю/нікотину і `λ = 0,25` (рішення людини №4).** Вхід — базова готовність м'яза на момент початку тренування
(`muscleReadiness(завершені_до_старту, workoutStart, 0)`): без `recoveryBoost` і без модифікаторів алкоголю/нікотину всередині моделі, щоб бак був детермінованою функцією залогованих
даних і не стрибав від станів поза сесією. Лінійна рампа `recovery.ts` — практична евристика (research §5), а не фізіологічний вимір; продуктивність усередині сесії страждає менше, ніж
відчуття готовності (Д№16: через 24 год CMJ −9,6 %, коли «відсоток відновлення» вчорашніх грудей ≈ 0,25; крепатура пікує саме тоді). Тому дефіцит готовності входить із вагою `λ`,
а не дослівно. `λ` — припущення, якорене в Д№16, не виміряне.

### 2.2 Інваріанти (що гарантує форма)

- **Монотонність (ревізія):** `T_prev` = рівень кінця попереднього сету, тож для двох суміжних подій м'яза без справжньої перерви `before_k ≤ tank_{k−1}` і `tank_k ≤ before_k ≤ tank_{k−1}`: **бар не зростає між сусідніми сетами** (довільний відпочинок < 3 год, довільна вага/повтори/RPE). Піднімає старт лише справжня перерва (≥ 3 год або заминка).
- **Межі:** `loss = c·T_k`, `0 ≤ c ≤ C_FAIL·1·1 < 1` ⇒ `T ∈ [0,1]`; `T₀ ∈ [1−λ, 1]`.
- **Без «другого дихання»:** відновлення діє лише на `Df` і обрізається рівнем кінця попереднього сету.
- **Причинність:** `T_k` залежить лише від подій перед `k` (RPE, відмова й повтори **цього** сету входять у `loss`, а не в `before`).
- **Відпочинок:** більше відпочинку не дає нижчого бака; у межах перерви < 3 год воно й не дає вищого (рівні).
- **Що НЕ гарантується (чесно).** (a) Вторинний м'яз: подія з `w = 0,5` лишає рівень, що дає `T_prev` його окремому ланцюжку; бари різних м'язів порівнювати не можна. (b) Монотонність «важчий попередній сет → не вищий стан пізніше» перевірена property-тестом лише для **наступного** сету; далі вона випливає з мультиплікативної форми `loss = c·T` не строго (дрібні частки відсотка). (c) Розрив ≥ 3 год або заминка піднімає бар (це свідомо). (d) Відпочинок як такий тепер майже нічого не змінює — див. наслідок у кроці 3; якщо продукт хоче бачити відновлення в бар під час сесії, це нове рішення людини (змінює модель і всі еталони).
- **Детермінізм:** функція від (`лифти`, `R`, `e1rmHist`, `PARAMS`); жодного `Date.now()`, `Math.random()`, стора.

### 6.1 Правило змін (заморожені параметри)

**Що робить модель.** `setTank.ts` обчислює для кожного сету бак цільового м'яза (на початку й у кінці сету): стартова готовність з минулих сесій
(`1 − λ(1−readiness)`), плюс втрати від усіх попередніх подій цього м'яза сьогодні (будь-яка вправа; вторинні ×0,5; суперсети — за мітками часу), де
втрата сету росте швидше за лінійно з часткою використаного запасу повторів (`u = reps/(reps+RIR)`), а частина втрати (`φ`) відновлюється відпочинком з напівчасом `h`.
Рівень бака ніколи не піднімається вище, ніж був перед попереднім сетом.

**Навіщо.** Одна зрозуміла смужка замість змішування «залишку» й «внеску в ріст»; прибрати «друге дихання»; врахувати відпочинок, дропи й суперсети.

**Інваріанти (порушення = баг):**

1. `0 ≤ tank ≤ before ≤ 1`; для суміжних подій м'яза без справжньої перерви (< 3 год, без заминки) `before(k) ≤ tank(k−1)` і `tank(k) ≤ tank(k−1)`: бар не зростає між сусідніми сетами.
2. Немає «другого дихання»: на `before(k)` не впливають RPE/відмова сету `k`; відпочинок (< 3 год) ніколи не піднімає старт вище кінця попереднього сету.
3. Детермінізм і причинність: чиста функція входів; бари ранніх сетів не залежать від пізніших; нічого з `Date.now()`, стора, DOM, `Math.random()`.
4. Відпочинок рахується по м'язу з міток сетів (`restBeforeSet`-семантика); більше відпочинку не гірше.
5. Кожен сегмент дропу рахується; відмова/RPE/`partials` перекривають оцінку Epley.
6. Жодних нових полів даних; смужка не змінює жодного числа статистики (§5).
7. Параметри — іменований об'єкт `TANK_PARAMS` (Object.freeze) у `setTank.ts`; тест порівнює його зі значеннями §2.1 (включно з γ і підлогою відображення).
8. Відображення безстанне: висота смужки залежить лише від `tank` цього сету; жодного авто-діапазону за іншими сетами.
9. Бари лише в живій сесії; `setHardness`, `fatigueSetCount`, `tiredVerdict`, `performanceDrops`, `muscleTally`, `carryOverSets` не змінюються заради смужки (тижнева втома не рухається).

**Правило.** Не змінюй параметри чи формули `setTank.ts` без одночасного оновлення (a) `docs/research/set-bars-fatigue.md` (новий рядок джерела або
позначка «припущення»), (b) цього spec (§2.1, приклади §3), (c) регресійних тестів із пов'язаними числами. Тест не послаблюється, щоб «стало зеленим» (CLAUDE.md, інваріант 7):
якщо еталонне число змінилось — спершу пояснення, яке рішення людини це змінило. Нове джерело, що суперечить параметру, — спершу в дослідження, потім у код.

## 8. Ризики і рішення людини

**Ризики**

1. **Параметри без калібрування.** Чотири з п'яти — припущення без джерела; найчутливіші `φ` і `C_FAIL` (таблиця §2.1). Мітигація: параметри заморожені, правило змін §6.1.
2. **Бак ≠ ріст.** Поруч живуть дві метрики («бак» і «цінність наступного сету»); користувач може їх плутати. Підписи/легенда — окреме рішення UI.
3. **Шум входів.** RPE недооцінює запас у середньому на ~1 повтор (Д№11); e1RM з Epley розходиться між людьми й вправами (Д№27–28). Бак — оцінка, не вимір.
4. **`readiness` як вхід.** Враховує лише останню сесію, дозу з розминками, лінійну рампу (Д§5): якщо числа з `recovery.ts` зміняться, бак зміниться разом із ними (це бажано, але впливає на еталон AC9).
5. **Старі дані.** Без `loggedAt` бак менш точний (fallback); для backfill-сесій він наближений.
6. **Бак швидко падає від першого сету** (рішення №1: після одного сету 8×80 RPE 8 — 0,685, висота 0,44), а 5 сетів до відмови дають підлогу (0,055); колір після ревізії насичується повільніше (`TANK_RED` 0,8). Якщо на скріншотах (AC12) вигляд не читається — міняти γ/`TANK_RED`/`C_FAIL`, а не форму моделі.
   6a. **Відпочинок майже не впливає на бар** (наслідок храповика на рівні кінця): бар = накопичена вартість сетів з `T₀`; `h`, `φ` діють лише після справжньої перерви. Це рішення рев'ю, не людини; якщо потрібне видиме відновлення — окреме рішення зі зміною моделі.
7. **Мертвий код:** `setStimuli` без споживача в продукті (лише тест-знімок) — свідомо лишений за рішенням №5.
8. **Перерахунок «заднім числом» зникає, але вид минулих екранів/скріншотів відрізняється від поточного** — очікувана зміна.
9. **Немає незалежного `stimulus.test.ts`** (раніше spec припускав його існування): контракт тижневої втрати тепер — `stimulusContract.test.ts` + `failure.test.ts`.

**Рішення людини (2026-10-17; замінюють відкриті питання)**

1. **Висота = бак у КІНЦІ сету** (після вартості сету й храповика), не на початку. Свіжий перший сет уже показує свою вартість. `before` (старт) лишається в результаті для тестів/майбутнього UI.
2. **Адаптивна шкала відображення — безстанна й монотонна:** `display = max(0,1; 1 − (1 − T)^0,5)`; колір = `max((1−T)/0,8; performanceDrop/dropTolerance)` (0,5 → 0,8 після рев'ю) (clamp 0..1) із збереженням `performanceDrops()`. Авто-діапазон за min/max відхилено (змінює раніше намальовані смужки; див. §2 «Відображення»).
3. **Бари лише в живій сесії** (як зараз, `live`), для **усіх** силових вправ, включно із суперсетами/групами й дроп-сетами; у завершених/`past` переглядах не додаємо.
4. **Готовність:** `muscleReadiness()` з `recovery.ts` на момент старту тренування, базова, **без** boost/алкоголю/нікотину в моделі; `λ = 0,25`; обґрунтування — §2.1.
5. **`setStimuli`/`priorBefore`/`marginalStimulus` лишаються експортованими з тестами** (контракти; `marginalStimulus` живе у `MuscleStatePanel`/`SessionView`); смужки перестали читати `setStimuli`. Числа `setHardness`, `fatigueSetCount`, `tiredVerdict`, `performanceDrops`, `muscleTally`, `carryOverSets` не змінено. У `SessionView` локальні `priorBefore`/`firstAt`/`rowMeters` видалено (мали єдиного споживача — смужку).
6. **`RIR_SEG = 1`** і «останній сегмент дропу — до відмови» прийняті як явні припущення; `φ`, `C_FAIL`, `p`, `h`, `λ` — як у §2.1, заморожені розділом §6.1.
7. **Калібрування на логах поза скоупом** (беклог, Д§7): параметри лишаються припущеннями до окремої задачі; змінювати їх лише за правилом §6.1.

**Зміна після рев'ю коду (2026-10-18; не рішення людини, потребує її підтвердження).** (1) Храповик — на рівні кінця попереднього сету; справжня перерва (≥ 3 год, заминка) його знімає. (2) `TANK_RED` 0,5 → 0,8. (3) NaN/Infinity у повторах санується до 0. Причина — знайдені рев'ю підйоми бара між суміжними сетами; наслідок (відпочинок не піднімає бар) описано в §2 крок 3 і ризик 6a. Рядки джерел у `docs/research/set-bars-fatigue.md` не змінювались (храповик там не описано).
