# Patch-coverage — spec

Задача: SPO-268 · Статус: у роботі · Власник: Mykola · 20.10.2026

## Мета і контекст

Власник хоче дуже швидкий pre-push і CI. Повне покриття клієнта (`client_full_baseline` ≈62%, SPO-49 у Backlog) на кожен push дорого й ще не досяжне як гейт. Тому: перевіряти покриття **лише змінених у diff виконуваних операторів `client/src`** (patch-coverage), а повний гейт (`test:coverage`, `coverage:guard`) лишити в CI без змін. Принцип «пороги лише ростуть» (SPO-47) зберігається.

## Поза скоупом

Підняття загального покриття (SPO-49/56); покриття `server/`, `functions/`; гілки/функції патча (спершу лише оператори); коментар у PR зі звітом.

## AC

- [ ] Скрипт `scripts/patch-coverage.mjs`: diff → змінені рядки продуктового коду, злиття v8-звітів, % покритих змінених операторів, перелік непокритих рядків · доказ: `tests/patchCoverage.test.ts`
- [ ] Pre-push: `client-tests-changed` збирає покриття тими самими related-тестами, падає нижче порога · доказ: червоний/зелений прогін, заміри часу
- [ ] CI: шарди збирають покриття лише змінених файлів, job `Patch coverage` зводить і падає нижче порога; повний гейт без змін · доказ: зелений CI + час ≤5 хв
- [ ] Поріг у `coverage-thresholds.json` (`patch.statements`), `coverage:guard` не дає знизити · доказ: `tests/coverageThresholds.guard.test.ts`
- [ ] ADR 007 + рядок у правилах

## Підхід

Аналог: `scripts/check-coverage-thresholds.mjs` (AST/JSON, чиста логіка + CLI) і крок `client-tests-changed` у `.githooks/pre-push`. Рекомендовано: **v8 `coverage-final.json` + власний підрахунок** (без нових залежностей). Оператор «змінений», якщо його початок у доданому рядку `git diff -U0`.
Альтернативи: (1) `diff-cover`/Codecov patch — залежність або зовнішній сервіс, формат lcov, повільніше; (2) гейт на весь файл (touched-file coverage) — суворіше, але штрафує дрібні правки у великих файлах (`LandingDesign.tsx` 4 тис. рядків).
Що не рахується: тести, сторі, фікстури, `.d.ts`, `main.tsx`. У pre-push файли `src/atlas/**` не оцінюються (їхні важкі тести виключені з швидкого кроку; оцінює CI).

## Вплив

UI-кіт — немає. Дані/безпека — немає. i18n — немає. CI: +1 легкий job (~20 с) і coverage-прапори в шардах (лише змінені файли). Ризик: v8-інструментування шардів може трохи сповільнити їх — міряти (ADR 007).

## План тестів

Юніт: розбір diff, злиття шардів, підрахунок, відсутні дані → помилка, ratchet порога. Інтеграція: демо-файл без тесту → pre-push падає (40%); з тестом → 100%.

## Реліз і відкат

Поріг стартує з 80 і лише росте. Відкат: прибрати крок із pre-push/CI (скрипт ізольований).

## Партії

1. Скрипт + тести + поріг/ratchet (AC1, AC4)
2. Pre-push + CI + ADR (AC2, AC3, AC5)
